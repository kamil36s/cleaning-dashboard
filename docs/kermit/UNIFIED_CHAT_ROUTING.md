# Unified Kermit conversation routing

The dashboard uses one Kermit panel and `POST /api/kermit/v1/chat`. The service chooses `GENERAL_CONVERSATION`, `PROJECT_GROUNDED`, or `CLARIFICATION_REQUIRED`. The existing `/ask` remains a grounded compatibility endpoint. Quick and Normal select performance budgets only.

## Request and response

`/chat` accepts `contractVersion: 1`, `message` (1–500 characters), `profile` (`quick` or `normal`), optional `history`, optional `conversationState`, and optional `allowMemoryPressure: true` after an explicit YELLOW confirmation. Only `user` and `assistant` history roles are accepted. At most 12 history messages, 1,200 characters each and 3,000 characters total are admitted; the whole JSON request is limited to 16,384 bytes. Unknown fields and duplicate JSON keys are rejected. The browser keeps history in memory, trims it before requests, and deletes history and route/topic hints when Clear conversation is pressed. No conversation database or localStorage history is added.

The response adds `route` and `topic` to the existing answer fields. Project answers retain service-owned citations, uncertainty, findings, and `evidenceAsOf`. Ordinary answers have no citations and `groundingStatus: not_required`. `timing.routingMs` and `timing.classifierCalls` describe routing cost.

## Router and continuity

`kermit_service/routing.py` applies deterministic rules in order: greetings and explicit topic switches, private runtime requests, explicit verification instructions, hypothetical improvement prompts, current implementation questions, contextual follow-ups, then general conversation. It recognizes reviewed subsystem names and a small set of aliases. A short reference to a known project topic uses grounded retrieval; a follow-up to an ordinary exchange stays conversational; a reference without usable earlier context yields clarification. A newly named subsystem replaces the previous topic; an ordinary topic switch resets it.

The latest message controls routing. Earlier **user** messages and an optional browser route/topic hint can help interpret a follow-up. Assistant history is never used as proof of implementation or as a routing authority. The service constructs prompts itself. It does not accept browser-selected routes, models, endpoints, source paths, tools, or capability flags. No classifier model call is currently used: deterministic cases avoid a second Qwen inference and unresolved references ask for clarification. Evaluation should revisit that trade-off only if measured route errors justify the CPU and latency cost of classification.

For a grounded follow-up, the service derives a short focus from the prior same-topic **user question** and expands the retrieval question with the topic. It does not copy an earlier assistant answer into the EvidencePack. The Cleaning daily-goal follow-up also ranks the admitted capacity and recovery-day evidence above unrelated use of “change”; the Quote provider questions rank the admitted provider relationship and names. These are selection hints only: Phase 3 admission, Phase 4 limits, and Phase 6 draft validation, claim grounding, conflict handling, and service-owned citations remain the same. Missing, stale, or insufficient evidence still yields a limitation. A question for a live private value receives a direct limitation because this phase has no authorized runtime adapter.

General conversation uses the configured local provider, Resource Gate, and the same generation semaphore as grounded drafts. The provider receives a fixed system instruction and bounded untrusted history, without tools or retrieval. Its structured answer must contain empty evidence arrays. Project improvement prompts include only prior **user** turns; replies asserting current behavior or omitting proposal language are withheld. If a proposal draft is malformed, the service returns a clearly marked generic hypothetical suggestion. If a user requests an exact current implementation fact, routing uses the grounded path. General model output is not treated as verified repository evidence.

The service retains loopback binding, Host/Origin checks, model concurrency protection, GREEN/YELLOW/RED memory admission, and keep-alive configuration. The dashboard remains usable if Kermit is unavailable. No model can read files, call APIs, execute shell commands, query SQL, or mutate the app.

## Evaluation and limits

`tests/test_kermit_unified_chat.py` covers 19 route scenarios, follow-up query expansion, rejected fabricated assistant history, ordinary/proposal/private-data response behavior, and deterministic routing cost. Existing service, grounding, Phase 8, and browser suites remain regression gates. A deterministic router can still misunderstand unusual phrasing; a short clarification or a conservative grounded route is preferable to an unsupported implementation claim. Broad general model output is filtered by a bounded validator, but it is not a source of project facts. No historical ChatGPT archive or private journal is indexed.

On the local host, 10,000 high-confidence deterministic routes averaged 0.0114 ms each; classifier calls were 0. In the final real Quick-profile HTTP sequence, greeting took 11.9 s, grounded Cleaning explanation 30.3 s, grounded follow-up 28.6 s, hypothetical improvement 13.3 s, and joke 15.0 s. The private unindexed journal limitation returned without generation. Cold available RAM was 7,748 MiB and observed resident-call checks ranged from 3,573 to 4,070 MiB; all calls stayed GREEN. The Quote cross-subsystem regression ran through `/chat` in Quick and Normal with four service-owned citations and the correct browser/provider relationship. Hashes of 134 admitted sources and six core index files were unchanged across the final conversation. The index validated with zero stale or missing sources. This evidence index publishes a build fingerprint but no wall-clock `evidenceAsOf` timestamp, so the UI displays the fingerprint and cannot show a timestamp that the contract does not contain.
