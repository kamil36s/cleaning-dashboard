# Phase 7.1: automatic local service startup

The normal Windows dashboard launchers ensure that the independent Kermit HTTP service is available on `127.0.0.1:8767`. `start-dev.cmd` runs `scripts/kermit-autostart.js` before the API, Network Monitor, and Vite. `start-dashboard.ps1` and `start-all.ps1` reach that path through `start-dev.cmd`. The shortcut path in `scripts/launch-dashboard.ps1` also runs the check when it finds an already running dashboard and only opens the browser. None of these hooks changes the independent Live Workout runtime.

The launcher sends a bounded `GET /api/kermit/v1/status` to the fixed loopback address with an allowed Origin. It requires HTTP 200, the reflected exact Origin, contract version 1, service availability, a known model state, offered Normal profile, a recognized index state, `serviceBuild: unified-chat-v1`, and `chat@1` in `capabilities`. It also checks that `OPTIONS /api/kermit/v1/chat` returns the allowed Origin and POST method. A compatible service is reused. If the port refuses connections, the launcher starts `python -B -m kermit_service` hidden and detached, then probes readiness for up to 18 seconds. A healthy Kermit status without the current chat capability is reported as `restart_required`; an unrecognized listener is reported as a conflict. Neither is silently reused. Kermit failure does not stop dashboard startup.

`KERMIT_AUTOSTART=false` (also `0`, `no`, or `off`) disables the launcher check and automatic start. The Phase 7 panel flag, `KERMIT_ENABLED`, is separate; disabling service autostart does not disable any dashboard feature. The service still binds only to loopback, and its strict Host and Origin policy is unchanged. The launcher fixes its local service address to match the current frontend endpoint. This phase does not expose Kermit to the LAN.

The service launched this way is a persistent independent local process. The launcher records its child PID and random service `instanceId` in a per-workspace file in the OS temporary directory only after the status PID matches the spawned child. If a later launcher finds that exact recorded instance incompatible, it rechecks the live status and verifies through Windows that the PID still owns the loopback listener, stops only that PID, waits for the port to become vacant, and starts the current service. Dashboard shutdown and `stop-dev-services.ps1` do not stop Kermit. A manually started service, a listener without a matching ownership record, or a changed listener is never stopped automatically; the launcher reports `restart_required` for the old service. There is no background restart loop or broad process-name termination. To remove Kermit from the dashboard, disable autostart and the separate panel flag; a running service can be stopped by an administrator after verifying the listener's process identity.

Service startup only constructs the HTTP handler. The status probe reads Ollama's installed/resident model lists and the existing index freshness metadata; it sends no chat request, runs no model warmup, builds no index, and accesses no application runtime database. A nonresident available model normally reports `sleeping`; unavailable Ollama/model reports `unavailable`. The existing Resource Gate still controls the first question, including GREEN/YELLOW/RED rules and two-minute model keep-alive. The dashboard loads even if the model is unavailable or RAM is below model-load thresholds.

The panel performs a status check on mount and on open or explicit Check again. It displays the service/model state and index state. If the service starts after a failed check, opening the panel or clicking Check again recovers without idle polling. An index reported `stale` or `unavailable` is not rebuilt at startup; retrieval keeps its existing fail-closed behavior. Only the trusted development workflow may explicitly run `python -B -m kermit_index build` and then `validate` after admitted source changes.

## Unified chat compatibility incident

On 2026-09-30 the process already listening on port 8767 had started before `/chat` was introduced. It returned a healthy v1 `/status` with a current index but had no build/capability fields; `OPTIONS /chat` returned 403 and a direct `POST /chat` returned 404. The old launcher reused it because it checked only `/status`. In the actual browser, the failed OPTIONS preflight blocked the POST and surfaced as `TypeError: Failed to fetch`, which the old panel called a generic outage. The compatibility check above now rejects that precise state. The panel shows a restart-required message and disables Send while keeping the reported index state visible. When the listener has no matching launcher ownership record, an operator must verify and stop that specific instance before the launcher can start the current service.

Kermit may know, read and explain. Kermit may not act. The fixed launcher operation is outside the model and introduces no model tool, runtime reader, ChatGPT-history access, or command capability.

## Verification on 2026-09-30

The normal `scripts/launch-dashboard.ps1` path reused the already healthy Kermit instance and opened the dashboard; the independent Training Runtime reported ready. The service remained nonresident until a question: status was `sleeping`, GREEN, with 102 current indexed sources and no stale or missing sources. A real Quick request, “What does the Quote widget do?”, returned `status: ok`, `groundingStatus: grounded`, and a service-owned citation to the reviewed Quote pack. The model then reported `ready`; the index build fingerprint stayed unchanged across the request. Earlier in the same check, source-document edits surfaced as stale until the index was explicitly rebuilt and validated. The already running service was not stopped, so a fresh-process live launch was covered by deterministic fake-process tests rather than by terminating that instance.
