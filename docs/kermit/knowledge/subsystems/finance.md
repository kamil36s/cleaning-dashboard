## Purpose and boundaries

Finance owns bank transaction import and classification, categories/merchants/rules, accounts, budgets, planned items, obligations and occurrences, goals, analytics, review/audit, receipt evidence, and finance-specific settings. It does **not** own bank accounts at the provider, external bank synchronization, Anki/Language state, or generic dashboard widget layout. The dashboard budget card reads Finance overview; the separate Bills widget reads Finance obligation/occurrence projections. Receipt OCR is an input/evidence boundary, not the authority for bank transaction amounts.

The write boundary is `server.py` -> `FinanceService` -> feature services -> `FinanceRepository.transaction`. `FinanceService` composes `FinanceOperationsService`, `FinancePlanningService`, `FinanceAnalyticsService`/`FinancePeriodService`, `FinanceReviewService`, and `FinanceReceiptService`. Repository methods own SQL, schema migration, transactions, account identity, import links, and rollback. `finance_importer.py` parses CSV; `finance_classification.py` assigns canonical semantics; `finance_receipt_parser.py` deterministically interprets OCR evidence.

## Data flow

**CSV import.** `server.py::import_budget_csv_from_payload` validates base64 and byte limit, then `FinanceService.import_csv` creates an import batch. `finance_importer.py::parse_csv_bytes` decodes UTF-8 BOM or CP1250, identifies supported columns/statement format, validates dates/money/currency/rows, normalizes text, masks accounts, and computes a SHA-256 transaction fingerprint from date, signed minor units, currency, normalized description, keyed account identity, and an occurrence ordinal. Bank category/balance/annotation are excluded from base identity. Within one repository transaction, service resolves/matches accounts, updates eligible balance snapshots, finds exact or cross-format matches, inserts new transactions, classifies them, and associates every accepted source row to the batch. Duplicates retain batch association; invalid/filtered counts and errors remain in batch metadata. Failure marks batch failed. `rollback_batch` protects transactions linked to other batches. `tests/test_finance_import.py` covers overlap, identical-day occurrences, and rollback.

**Classification and review.** `finance_classification.py::classify_transaction` uses imported defaults/merchant matching and ordered active rules; `FinanceOperationsService.manual_update` and rule apply are explicit mutations. `classification_explanation` exposes source/reason. `FinanceReviewService` groups normalized description/family/merchant evidence, calculates issue counts, offers suggestion/preview, applies within a transaction, records audit rows and supports latest undo. Receipt item review is a separate review path. Ambiguous or incomplete classifications remain reviewable; a heuristic is not silently promoted to manual truth.

**Planning.** `FinancePlanningService.save_obligation` validates kind, cadence, dates and amount; `_generated_occurrences` expands active confirmed obligations through the requested window and applies stored occurrence overrides. `set_occurrence_status` stores user decisions. `bills_payload` adapts occurrences to the Bills widget; `upcoming` excludes paid/matched/skipped/dismissed by default. Budgets, planned items, account roles, safe-spend settings, and goals have their own canonical tables and mutation methods. `simulate` is explicitly nonpersistent.

**Receipts.** `FinanceReceiptService.import_bytes` detects source format; `ReceiptImporter` parses structured JSON, PDF text, image/PDF OCR evidence. `LocalTesseractOcr` is optional desktop OCR; Android ML Kit is external structured evidence. `finance_receipt_parser.py` performs deterministic normalization/line and total reconciliation, with geometry/confidence/review reasons. Service preserves originals privately, deduplicates source/receipt identity, records items/products and matching state, and links to a bank transaction only through matching/manual review. Reprocessing preserves manual decisions and existing facts on failure (`tests/test_finance_pack_d1.py`). Receipt evidence can split category analytics but does not change transaction amounts (`tests/test_finance_pack_d.py`). There is no finance receipt worker queue in this path; imports/reprocesses are request-triggered.

## Metrics and calculations

Canonical monetary fields discussed here are stored in integer minor units and API amounts below divide by 100; the widget formats PLN with `Intl.NumberFormat("pl-PL", {style:"currency"})`. Calendar month and range filters use ISO `transaction_date` inclusive `BETWEEN`; `FinancePeriodService.resolve` supports current/latest-data/previous month, rolling 7/30/90 days, calendar year, and custom inclusive date range. `_parse_date` defaults to UTC date when no reference is supplied; some planning methods use local `date.today()`, so cross-midnight comparisons warrant explicit `referenceDate` when testing (F-02).

| User-visible metric | Inputs, filter and exact rule | Null/format, owner/test |
| --- | --- | --- |
| Period expenses/income/savings/net | `FinanceAnalyticsService.get_period_summary`: within inclusive dates, expenses = sum of `-amount_minor` for negative `expense`; salary + positive `income` = total income; savings = absolute `saving`; refunds = positive `refund`; net = income + refunds - expenses - savings. Transfers excluded from net. | PLN; empty sums 0. `tests/test_finance_pack_b.py`. |
| Savings rate / daily average | Same summary; `100*savings/total_income`; expenses divided by inclusive day count. | Rate null if income 0; average PLN/day. `tests/test_finance_pack_b.py`. |
| Merchant breakdown and daily cash flow | `FinanceAnalyticsService._breakdown` groups absolute amounts for `expense` by merchant ID; `get_cash_flow` groups salary/income/refund/expense/saving by `transaction_date` and applies the net formula per day. | PLN, per merchant/day; `tests/test_finance_pack_b.py`. |
| Category analytics with receipt split | `FinanceService.analytics_payload("categories")` calls `FinanceReceiptService.analytics_category_breakdown`: each expense in inclusive period uses its transaction category by default. A linked receipt replaces that one amount with item effective amounts (item total minus discount) plus adjustments only when receipt validation is valid, every item maps to a Finance category, receipt total matches transaction amount within 1 minor unit, and composition total also matches within 1. Otherwise retain the transaction category. | PLN, category/adjustment grouping; unique transaction IDs count once per bucket. `tests/test_finance_pack_d.py::test_split_analytics_replace_transaction_category_without_double_counting`. |
| Period comparison | `compare_periods`: current minus previous-equivalent; percent = difference * 100 / abs(previous). | Null percent if previous 0. `tests/test_finance_pack_b.py`. |
| Budget pace / suggestion | `FinancePlanningService.budget_status`: monthly expense sum by category (including child) / limit * 100; elapsed = reference day / days in month * 100; projected = spent / elapsed fraction while 0<elapsed<100. Suggestion = ceiling of historical monthly average to 5000 minor units (50 PLN). | Used/elapsed/pace points rounded 1 decimal; projected PLN; zero-limit used 0. `tests/test_finance_pack_c.py`. |
| Goal progress | `goals`: allocated is linked positive account balance if available, else stored allocation; remaining max(0,target-allocated); progress min(100, allocated/target*100); completion month uses ceil(remaining/monthly contribution). | Target validated >0; absent contribution/date gives null completion. `tests/test_finance_pack_c.py`. |
| Safe to spend / per day | `safe_to_spend`: included spending-account liquid balances (stored or latest raw balance fallback) minus outstanding confirmed obligations through horizon, included planned expenses, planned savings, and configured buffer. Days = max(1, inclusive horizon-day span); safePerDay = floor(safe minor units/days). | Signed PLN; may be negative. `next_income` falls back to month end with `nextIncomeUnknown` if no income event. `tests/test_finance_pack_c.py`. |
| Forecast / report / trends / subscriptions | `forecast` starts from liquid balance and cumulatively applies generated obligation and planned-item signed events; `report` groups current/previous calendar month and top expense categories/merchants; `trends` groups by YYYY-MM; `subscriptions` annualizes cadence with factors weekly 52, monthly 12, quarterly 4, annual/once 1. | PLN; report savings rate null for zero income; `tests/test_finance_pack_c.py`. |
| Data quality and review load | `FinancePlanningService.data_quality` counts all transactions and non-null merchant/category/kind fields; coverage = populated/total * 100 (100% for empty DB). `FinanceReviewService._metrics_for_model` instead uses category-required kinds and merchant-relevant kinds for its coverage; unresolved issue count excludes decisions marked ignored/resolved. | Percent rounded 1 decimal; counts in records/groups/issues. `tests/test_finance_pack_c.py`, `tests/test_finance_pack_c6.py`. |
| Recurring candidates | `FinancePlanningService.recurring_candidates` excludes transfer/saving, groups by merchant identity, kind and category, requires at least 3 occurrences, median interval in weekly 5-9, monthly 25-35, quarterly 75-100, or annual 330-400 days, with at least 60% intervals inside the same band. Amount variance = (max-min)/mean * 100. | Candidate is unconfirmed, excluded from forecast until saved as obligation; variance rounded 1 decimal. `tests/test_finance_pack_c.py`. |

The dashboard widget displays `overview` values without recomputing these formulas. `FinancePlanningService._freshness` labels latest transaction age 0-3 days `fresh`, 4-14 `aging`, later `stale`, or `empty`. `FinancePeriodService.freshness` uses a separate current/stale threshold of one day; see F-03. The report's top categories use transaction categories, while the categories analytics route can use receipt splits; see F-04.

## Jobs, integrations, dependencies, failure and recovery

Durable finance queue/worker: **None identified** for CSV import, receipt OCR, classification, or planning; these are synchronous request/service operations. Retry/backoff/cancellation/concurrency controls for a queue: **Not applicable**. SQLite transactions roll back partial writes; import batch status records failure. Startup initialization applies missing schema migrations and compatibility migrations; private backups are made for specific legacy/privacy transitions. A failed OCR path keeps receipt evidence for review rather than inventing a total. User-triggered reprocess, review correction, import rollback, and backup recovery are distinct actions. External integration: local Tesseract and Android ML Kit evidence input; no direct bank API. Rates/retries for Android transport are outside this Finance pack.

## Privacy and security

Finance DB, original receipt files, imports, private backups, and account key are excluded from Kermit static admission. `server.py` private path deny and `vite.config.js::FINANCE_PRIVATE_PATH` prevent direct static exposure. Public Finance API responses may still carry personal financial values, so future Kermit must not treat route existence as authorization to call it. This pack reviewed source/schema/tests only; it contains no live amounts or receipt content.
