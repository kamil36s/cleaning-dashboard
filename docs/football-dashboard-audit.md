# Football Dashboard: audit and implementation status

## Existing pipeline

`kitchen.html` loads `js/kitchen.js`, which requests `/api/kitchen/scores` from `server.py`. The server reads `data/kitchen-settings.json`, selects entries from `KITCHEN_LEAGUES` and `KITCHEN_NEXT_TEAMS`, fetches provider data, normalizes individual responses, deduplicates matches, adds crests, builds slides, and writes `data/kitchen-scores.json`. The browser performs a second slide normalization and rotates the result. `/api/kitchen/debug` reports selected sources, cache counts, and some errors. The existing Kitchen settings UI lives in `settings.html` and `js/settings.js`.

Sources: API-Football is used for results and tables if `API_FOOTBALL_KEY` is set. ESPN and TheSportsDB provide results, fixtures, and live scores; tables use ESPN, TheSportsDB, API-Football, and BBC fallback by league. A CONIFA path reads Wikipedia data. Manual supplemental results and next fixtures are embedded in the server. No football news source exists. API keys are server side. TheSportsDB league catalog is cached in `data/kitchen-leagues.json`; team crest candidates are cached in `data/kitchen-team-crests.json`.

The Kitchen score cache has a 30-minute TTL, fixtures have a 2-hour TTL, tables have a 6-hour TTL, and the league catalog has a 24-hour TTL. There is no dedicated football worker. Kitchen browser polling drives refresh, every five minutes normally and every 30 seconds while a live game is shown. Before request control was added, each score request could make live provider calls even while the score cache was fresh. Identical provider requests from settings and Kitchen could also overlap. The new in-memory request control deduplicates equal URLs briefly, applies provider rolling-minute budgets, honors HTTP 429 `Retry-After`, and cools down after repeated failures. It does not provide a persistent quota ledger across server restarts.

The currently enabled football clubs include Liverpool, Beşiktaş, Wieczysta Kraków, Hutnik Kraków, and Poland. The settings also include Montreal Canadiens, which is hockey and must remain untouched by football configuration. Many competitions are enabled, including Premier League, Ekstraklasa, and Polish I Liga. The provider catalog contains more competitions than are followed.

## Likely causes of inconsistent display

- Results are intentionally removed once outside the configured recent-hours window (currently 24 hours); upcoming fixtures have a different TTL and time window.
- Provider calls are mixed, and some adapters catch errors and return empty lists. A blank result was not distinguishable from a provider failure in the existing debug view.
- `dedupe_matches` identifies a match by league key, normalized display names, and played date. Different aliases can evade deduplication; similar names can collide. The kept provider is determined by fetch order, so its crest and metadata may differ from another source.
- The fallback path can return old cached data while setting a new `updatedAt`, obscuring the age of the underlying response. The desktop view therefore reports the file cache age, not proof that every match was reverified.
- Crest selection combines hardcoded known assets, match payloads, standings, and a name-keyed crest cache. The browser proxies images through `/api/kitchen/image`; a provider URL can be unavailable or blocked by the image host allowlist. Nation flags and club crests use different provider images.
- Live data was fetched for each score request even on a cache hit. The desktop page now reads the on-disk snapshot only, and marks old cached live rows unverified.

## Desktop design and safe sequence

`football.html` is the desktop UI. `/api/football` reads the existing Kitchen JSON snapshot and local SQLite history without making external calls. It exposes matches, clubs, competitions, following, cache ages, provider capabilities, errors, bounded request history, and recent sync summaries. Following uses the existing `/api/kitchen/settings` route and preserves non-football selections. `/api/football/settings` keeps Kitchen slide limits and category controls in a separate file; the existing Kitchen sports settings schema stays intact. News shows an explicit empty state until a permitted feed is configured. Provider request history records endpoint paths without query strings or credentials; the history is capped at 200 requests and 50 runs.

This is an adapter around the current system. `football_store.py` now retains normalized match snapshots, clubs, competitions, and provider mappings in `data/football.sqlite`; existing Kitchen files remain its refresh input. The next architectural step is to make provider adapters write through a canonical matching service with explicit rejection reasons, and to add table snapshots and approved news metadata. A persisted quota and retry controller should own refresh scheduling before desktop browsing expands beyond the existing Kitchen sources. Only then should Kitchen read from the new shared store; its current route and payload should remain compatible while consumers migrate. The old slide builder should be removed only after every caller is verified.

Current limits: historical matches begin accumulating only with snapshots observed after this implementation; older Kitchen results cannot be reconstructed. Tables are still only from the current Kitchen cache. The desktop cannot browse untracked leagues live, fetch news, explain every rejected provider row, or verify fresh live scores without a Kitchen refresh. BBC and Wikipedia fetches are not yet included in the bounded JSON request history. Provider health reflects the last observed request, not a separate active probe. Manual force refresh is intentionally absent until the persistent quota controller exists.

## News source review (29 September 2026)

The [BBC Sport RSS explanation](https://www.bbc.co.uk/sport/articles/cqllxj2n4kyo) describes published feeds and encourages headline display on websites with “BBC Sport” attribution, subject to its linked terms. The linked [RSS terms page](https://www.bbc.co.uk/terms/additional_rss.shtml) was inaccessible to automated review, so this project does not ingest that feed yet. The separate [BBC Information Syndication API](https://information-syndication.api.bbc.com/) requires a BBC relationship and API key; it is not a substitute for the public RSS feed. [UEFA's terms](https://www.uefa.com/news-media/news/0256-0dc91ad71f32-ce04913814f0-1000--general-terms-and-conditions/) prohibit automated collection of its platform content, so it is not a news ingestion source. Liverpool's [official news page](https://www.liverpoolfc.com/news) is useful for browsing but was not verified as a permitted RSS/API source. The News tab therefore remains an explicit empty state.
